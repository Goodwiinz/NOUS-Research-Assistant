# Local Codex harness bridge

**Status:** Implemented as a local Codex bridge feature; live acceptance requires a deliberately configured NOUS test project, paired device, and workspace, and has **NOT RUN** against a deployment. This document describes the current bridge contract. It does not cover cross-chat context synchronization or tracing. Through the opt-in local stdio MCP facade described in [NOUS read tools over MCP](#nous-read-tools-over-mcp), Codex can call NOUS read tools, publish one file from a registered workspace root as a NOUS artifact, request a project note that the user must approve in the browser, and request changes to the user's library (see [Library actions](#library-actions)), each only under a scope the user approved. Reading the project memories the user selected to share (`context:read`) is exposed through `--context` on `--project` connections only; artifact editing and artifact sharing are not exposed. A connection can instead be bound to one NOUS workspace (MCP-only) and can request `library:read` and `library:write`; under `library:write` the reversible library changes run without a per-action approval, while a folder deletion and an arXiv ingest still wait for one. See [Workspace connections and library scopes](#workspace-connections-and-library-scopes).

## User workflow

1. An owner runs `nous-harness connect` on the computer that will execute Codex. The CLI completes NOUS browser authorization, registers the device, and waits for browser consent to a project-scoped `harness:execute` grant.
2. The owner registers a local workspace root, starts `nous-harness run`, and selects **Local Codex**, the paired computer, and its workspace in the NOUS chat composer.
3. NOUS durably accepts the chat message and run before dispatch. The local bridge receives a fenced command over authenticated WSS and starts the pinned Codex app-server with the verified local policy. Persisted events flow back to the existing chat transcript.
4. Exact, one-time Codex command approvals and required input are shown in NOUS. The browser re-reads the saved request before a decision and sends only the decision plus the displayed target hash. The local CLI grant token never enters the browser.
5. If the browser disconnects, execution continues and NOUS can replay persisted events when the chat reconnects. Browser presence is not run ownership or terminal evidence.

The bridge requires WSS except for a loopback development backend. The server accepts plain WebSocket connections from `127.0.0.1` or `::1` only with `ENVIRONMENT=development` or `ENVIRONMENT=local`; shared deployments, including `ENVIRONMENT=dev`, retain the WSS requirement. Access JWT and grant validation still apply before acceptance and on every frame.

NOUS-native chat remains the default provider. Provider/device/workspace selection is scoped to the signed-in user and chat thread. The bridge does not search or continue other NOUS conversations or synchronize a context file. Codex reaches NOUS only through the opt-in MCP facade below, and only with the scopes approved for this device.

## NOUS read tools over MCP

`nous-harness mcp` is a local stdio MCP server (`packages/harness-bridge/src/mcp/`) that forwards `tools/list` and `tools/call` to the backend read gateway (`GET/POST /api/v1/integrations/tools[/read]`, gated by `NOUS_MCP_ENABLED`, default `false`). The backend owns the tool allowlist, JSON Schema catalog, argument validation, project scoping, and result bounds; the facade adds nothing a caller could use to widen them.

- **Read tools.** The catalog carries two kinds of tool. Project-scoped tools resolve the Collection from the grant, never from arguments (a workspace grant names it with the validated `project_id` selector, see [Workspace connections and library scopes](#workspace-connections-and-library-scopes)), and return `requested_documents_unavailable` for any document outside it (a foreign id and an unknown id are indistinguishable): `search_documents`, `list_project_documents`, `do_kb_retrieve`, `get_current_draft`, `get_document_content` (summary or full text, paginated by characters with `offset`/`limit` ≤ 48,000 and a `next_offset` to follow until it is `null`) and `retrieve_passages` (PostgreSQL full-text ranking over the project's documents, `document_ids` optional, `top_k` ≤ 20; the `answer_pdf_queries` analog that works with `DO_KB_ENABLED=false`), `find_researchers` and `get_researcher` (see **Researcher tools** below). Args-only tools take no identity and are dispatched before the project check: `search_arxiv` (120 s budget shared with the agent's slow tier, at most 20 results advertised, arXiv itself returns up to 5), `search_external_database` and `list_external_databases` (connector registry, at most 20 results), and `get_arxiv_paper_content` (full text of one arXiv id, paginated like `get_document_content`, cached in Redis: 24 h fresh, up to 7 d stale fallback when a refetch fails). `get_arxiv_paper_content` persists nothing; use `ingest_arxiv_papers` to add a paper to NOUS. `list_library` (scope `library:read`) acts on no single project either: it lists the folders of the grant's whole scope. Every result is capped at 64 KiB; upstream failures come back as stable tool errors (`upstream_timeout`, `upstream_unavailable`, `arxiv_unavailable`, `retrieval_unavailable`, `researcher_not_found`) and never carry exception text. `source_refs` list only observed identities: `document_id`, `draft_id`, `arxiv_id`, or `external_id` with its `connector`.
- **Researcher tools.** `find_researchers` (`query` 1-200 characters, `limit` ≤ 25, default 10) returns `{researchers: [{researcher_id, name, paper_count}]}` and `get_researcher` (`researcher_id`) returns `{researcher: {researcher_id, name}, papers: [{document_id, title, arxiv_id?, published?}], coauthors: [{researcher_id, name, paper_count}]}`, with `source_refs` of one `document_id` per listed paper (`find_researchers` returns none). Both read one source: `Document.document_metadata["authors"]`, the author list that arXiv ingest persists, of the live documents of the grant's project, or of the one a workspace grant selects (the same project-and-ancestors join as every other project-scoped tool). **Coverage is the author lists of papers ingested into that project.** Documents without an author list are invisible. NOUS stores no affiliations, institutions or career history for them, and the tools do not claim any. Because the index is the project's own documents, another project's papers and authors in the same organization can never appear, and an author who only wrote for another project answers `researcher_not_found`, the same as an unknown id. (The knowledge graph's `PERSON` entities are not used: the graph is scoped by organization only and carries no document ids, so it cannot be restricted to a project.) A `researcher_id` is the author's name casefolded with whitespace collapsed (at most 200 characters), so spelling variants merge and `name` is the newest document's spelling; two different people with the same name are one researcher. `find_researchers` matches the query as a case-insensitive substring and orders by paper count, then `researcher_id`. `get_researcher` lists at most 100 papers (newest `publication_date`/`published` first, then newest ingest) and at most 100 co-authors, counted over every paper of the researcher, not only the listed ones. The tools scan the 2,000 newest documents of the project in Python (O(documents × authors)); when a list is cut, by that scan window, `find_researchers`'s `limit`, the 100-item caps or the 64 KiB result cap (measured over the whole response, `source_refs` included), the payload carries `truncated: true`. When the scan window hid older documents, a `researcher_not_found` from `get_researcher` also carries `truncated: true` (still an error): the author may exist in a document that was not scanned. Live proof (ingest an arXiv paper into a dev project, then call both tools) has **NOT RUN**; the tests use SQLite project and document fixtures only.
- **Consent.** `nous-harness connect --tools` requests `harness:execute` plus `tools:read`; adding `--publish` also requests `artifacts:publish`, adding `--write` also requests `tools:write`, adding `--library` (which also needs `--write`) requests `library:read` and `library:write`, and adding `--context` requests `context:read`, the scope of `read_selected_context` (a project connection only; see **MCP-only** below). `--publish`, `--write`, `--library` and `--context` are refused without `--tools`. `--workspace WORKSPACE_UUID` replaces `--project` and binds the grant to a workspace instead of one project (see [Workspace connections and library scopes](#workspace-connections-and-library-scopes)). Every scope appears on the browser approval page, with a plain-language label beside its raw name. `tools:read` covers the whole read catalog above except `list_library` (`library:read`), including the arXiv and external-connector searches, which leave NOUS to query third-party services with the model-supplied query. A connection made without `--tools` has no MCP access and `mcp install` refuses with a reconnect hint. The stored scopes only decide whether the local process offers a tool; the backend re-checks the grant on every request.
- **Managed sessions.** When the local connection carries `tools:read`, `nous-harness run` adds a session-scoped `mcpConfig` entry that launches `nous-harness mcp --api ORIGIN --store DIR --session HANDLE` for that Codex thread. Argv contains only the API origin, the state directory, and the opaque credential handle; the CLI JWT and grant token are read from the owner-only store inside the child.
- **Standalone Codex.** `nous-harness mcp install` prints the `codex mcp add nous -- …` command for the user to run. The package never edits `~/.codex/config.toml` or any other global Codex configuration.
- **Transport hygiene.** Stdout is the JSON-RPC channel; diagnostics go to stderr. The API origin must be HTTPS, except the explicit loopback development hosts. Model-supplied arguments are sent only inside the invocation body; they cannot set headers, URLs, identity, or credentials. Gateway rejections are stable tool errors with no retry: 401 → reconnect with `--tools`; 403 → the grant lacks the scope of that tool (`tools:read`, or `library:read` for `list_library`) or the resource is outside the granted project or workspace (the bridge's message text still names only `tools:read` and the project); 422 → the gateway's own argument reason; 503 → NOUS's own reason (tools disabled, artifact publication disabled, or artifact storage unavailable). Network failures name the URL and the underlying cause on stderr. `run` logs a stderr notice when the connection has no `tools:read`, so a missing `nous` server is never silent.
- **Publication.** When the connection carries `artifacts:publish` (`connect --tools --publish`), managed sessions launch the MCP child with `--root <registered workspace root>` and the server offers `artifacts_publish` (`packages/harness-bridge/src/artifacts/`). Each call validates the relative path lexically, refuses symlinked or hard-linked files, then opens the file with containment enforced on the descriptor rather than the path string: macOS uses `O_NOFOLLOW_ANY` so the kernel refuses a symlink in any component (a directory swapped for a symlink after the path checks fails with `ELOOP`), Linux checks the opened descriptor's real path under `/proc/self/fd` against the root, and other platforms are refused. Size is compared before and after the open and the read is bounded to the validated size. The bytes are then reserved, uploaded and finalized through `/api/v1/artifacts` with the grant headers; the backend re-verifies size, digest and scope, and serves downloads as attachments with `nosniff`. Publication is gated by `ARTIFACTS_ENABLED` (default `false`), not by `NOUS_MCP_ENABLED`: with it off, reserve, upload and finalize answer 503 "Artifact publication is disabled". `mcp install` binds the single registered root, or the one named with `--root`; several registered roots require an explicit choice. A root that no longer exists at launch is logged to stderr and publication is simply not offered; read tools keep working. **The root is a publish scope, not a read boundary:** under Codex `workspace-write` the model can copy any file it can read into the root and publish it, exactly as it could write it to disk. That matches Plan 01's stated limit that folder registration is not read isolation. A workspace-bound grant cannot publish: the artifact routes answer 403.
- **Action requests.** When the connection carries `tools:write` (`connect --tools --write`, on either binding), the MCP child that managed sessions and `mcp install` launch gets `--actions`; when it also carries `library:write` (`--library`), it gets `--library` as well. Either flag makes the server also offer `request_action` and `get_action_status` (`packages/harness-bridge/src/actions/`). `request_action` takes an `action` from the catalogue in [Library actions](#library-actions), a client-generated UUID `invocation_id`, and only that action's own fields. For `action=create_project_note` they are a title (at most 255 characters), Markdown content (at most 200,000 characters) and up to 20 tags; identity and project come from the grant, never from arguments. It calls `POST /api/v1/integrations/actions`, which records the request idempotently by invocation ID and payload. A request that needs a decision returns `awaiting_approval` with an `approval_url` for the browser page `/integrations/actions/{invocation_id}`, and nothing changes until the signed-in requester opens that page, reviews the stored action and its target, and approves. A reversible library action requested under `library:write` runs inside the request instead, and the reply carries its outcome (see [Library actions](#library-actions)). The decision route (`POST /api/v1/integrations/actions/{invocation_id}/decision`) refuses every CLI token, so a harness cannot approve its own request. The `drain_integration_actions` beat task (every 2 s) claims each approved row with a conditional update, re-checks authority against the consent the grant was exchanged from rather than the short-lived grant token, and then runs the effect and writes its receipt in one transaction (the arXiv ingest is the one exception, see [Library actions](#library-actions)). A commit with an ambiguous outcome leaves the row `executing`. When `SWEEPERS_ENABLED` is on, `sweep_stale_actions` moves such rows to `outcome_unknown`, and they are never re-run. `get_action_status` reports `awaiting_approval`, `approved`, `executing`, `succeeded`, `failed` (including a denial) or `outcome_unknown`. `NOUS_MCP_ENABLED=false` rejects new requests, so nothing auto-runs either, and holds approved rows unexecuted, while status reads of existing requests keep working. The backend guard lives in `backend/src/services/agent/tool_actions.py`. A workspace-bound grant cannot request a note (`request_action` answers 422), but with `tools:write` it may request every library action, so a workspace connection gets `--actions` too (see **MCP-only**).
- **Grant renewal.** Integration grants live 15 minutes. The bridge and each MCP child share one credential handle and keep it fresh with `GrantKeeper` (`packages/harness-bridge/src/grants.ts`). Once the stored grant is 10 minutes old, it renews through `POST /api/v1/integrations/grants/{grant_id}/renew`. Long-running processes check every 2 minutes, and the replacement is written back to the owner-only store so other processes pick it up. Renewal revokes the old grant token and issues a new one with the same consent, binding (project or workspace) and scopes. It cannot widen scopes or revive an expired, revoked or consent-revoked grant. A publish sequence (reserve, upload, finalize) is pinned to one grant and starts only on a grant at most 5 minutes old. Connections made before renewal shipped have no stored grant ID, so they stop after 15 minutes and must reconnect.
- **Binding reuse.** `connect` reuses the stored connection, with no `/cli-auth/start` and no consent, only when all of these hold: a stored connection exists, `apiBase(apiUrl)` is unchanged, the project or workspace and `threadId` match (both absent counts as equal; a project and a workspace are different bindings), the stored scopes include every requested scope, and a forced `GrantKeeper.current(0)` renewal issues a new grant token. A transient renewal failure keeps the old token, so it does not count as proof. Otherwise the full flow runs. After a reconnect to a different chat, project or workspace is stored, the superseded credential handle is deleted locally. **Known gap:** the superseded server grant and consent are not revoked until `disconnect` (the grant lapses within 15 minutes; the consent does not). The probe forces a grant renewal, which revokes the previous grant token; running MCP children recover on their next call, but do not reconnect during an active publish sequence. `nous-harness status` reports the project and chat, or the workspace, device label, grant expiry (stored `renewedAt` + 15 minutes) and queue counts offline.
- **Handoff queue.** `handoff show|save|flush|list|discard` (`src/cli.ts`) and `save_nous_handoff` share `src/handoffs/queue.ts`. Each save is journaled as `handoff-<handoff_id>.json` (owner-only, through `CredentialStore`) before the POST, then deleted on 2xx, kept as `pending` on a network error, timeout, 5xx, 429, 401 or `GrantExpired` (with a reconnect hint for the last two), as `conflicted` with the 409 latest version (never merged), or as `rejected` on 403, 422 or another 4xx. `flush` is manual and has no daemon. It re-sends `pending` entries whose `thread_id`/`project_id` match the current binding with the same `handoff_id`, so the backend dedupes, and reports others as skipped. `handoff discard ID` removes one entry in any state and prints it. The MCP child journals only when `connection.json`'s `credentialHandle` equals its session handle, so a stale child cannot journal under, and later flush into, a newer chat binding. A pending MCP save names the queued `handoff_id`. A workspace connection has no chat, so the handoff commands refuse it. `handoff save` and `handoff flush` are intended hook targets; Codex hooks are **not wired** in v1 because per-harness hook support is unverified. Add a background retry only if pending entries are seen to accumulate.
- **Tests.** `packages/harness-bridge/test/mcp.test.ts` spawns both the managed configuration and the standalone command against a recording HTTP server and asserts identical `source_refs`, correct grant headers, JSON-RPC-only stdout, no secrets in the config or install command, and no writes under `CODEX_HOME`. `test/actions.test.ts`, `test/grants.test.ts`, `test/disconnect.test.ts`, `test/connect-reuse.test.ts` and `test/handoff-queue.test.ts` cover note and library action requests, renewal, disconnect, binding reuse and the handoff queue against stubbed HTTP responses. The backend action tests run on SQLite, so the conditional row claim under concurrent PostgreSQL workers is **NOT RUN**. The library actions' own tests are listed under [Library actions](#library-actions). Live acceptance against a real Codex and NOUS deployment is **NOT RUN** by these suites. Workspace scope resolution, the project selector and `list_library` are covered on SQLite by `backend/tests/unit/services/integrations/test_context.py` and `test_read_tools.py` (which also pin that `read_selected_context` is not a gateway tool), the refusal of `context:read` for a workspace binding by `test_context.py` and the read of a workspace-bound context by `test_selected_context.py`; catalog filtering and per-tool scope refusal over HTTP by `backend/tests/unit/api/test_integration_tools.py`; the refusal of workspace grants by the harness socket, the artifact routes and `request_action` by `backend/tests/unit/api/test_harness_workspace_guard.py`, `test_artifacts_api.py` and `backend/tests/unit/services/agent/test_tool_actions.py`; the `--workspace`, `--library` and `--context` flags (and the refusal of `--workspace` with `--context`) by `packages/harness-bridge/test/mcp.test.ts`, and workspace binding reuse (never across two workspaces, and not from a stored connection that holds both a project and a workspace or neither), `status` and the handoff refusal by `test/connect-reuse.test.ts`; and the approval page by the Vitest suites `frontend/src/lib/integrations/__tests__/scopeLabels.test.ts` and `frontend/src/components/integrations/__tests__/IntegrationApprovalPage.test.tsx`. ### Workspace connections and library scopes

Plan 07 Slice 1 lets a grant bind one NOUS workspace instead of one project, and adds the `library:read` and `library:write` scopes; Slice 3 adds the library actions that `library:write` runs (see [Library actions](#library-actions)). This section describes what the code does today. The approved design is [the Plan 07 design](../plans/2026-10-05-nous-mcp-alphaxiv-parity-design.md), a dated record and not a contract.

- **Binding.** A consent request, the grant exchanged from it and each renewal bind exactly one of a project (Collection) or a workspace. The request and context schemas enforce it, and so do CHECK constraints added by migration `hb03_workspace_grants`; an action row must name a target project, its grant's workspace, or both. A row that names both (a workspace grant's action aimed at one Collection) is authorised only by a workspace grant and consent of that workspace, and only while its project, and every other Collection it names (a move's destination), is still a live Collection of that workspace that the requesting user can reach; a project grant never authorises it, and a workspace grant never authorises a row bound to a project alone (`_authority_intact` in `backend/src/services/agent/tool_actions.py`, pinned by `test_tool_actions.py`). A workspace grant's library action on a folder stores such a row, with the folder in `project_id` and the grant's workspace in `workspace_id`; its `create_folder` stores only `workspace_id`, and runs only while the user can still reach that workspace. The workspace must be one the signed-in user owns or is a live member of, and a public workspace alone is not access. `authorized_scope` (`backend/src/services/integrations/context.py`) resolves what a grant may touch on every call: a project grant gets its one live Collection, and a workspace grant gets every live Collection of its workspace. A statement that lists the scope filters by the same scope as a SQL condition (`authorized_scope_filter`, which re-checks access first) and never binds the ids `authorized_scope` returns: PostgreSQL refuses a statement that binds more than 32,767 values, and nothing caps the Collections of a workspace, so an `IN` list of them would make `list_library` fail for every member of a large workspace. `test_list_library_binds_no_value_per_collection` pins it. A deleted workspace, a lapsed membership, or an inactive user or organization is refused with 403, and a deleted Collection drops out of a workspace grant's scope.
- **MCP-only.** A workspace grant can never hold `harness:execute`, `artifacts:publish`, `handoff:read`, `handoff:write` or `context:read`: `check_scopes` refuses them when consent is requested and on every use, and the harness socket and the artifact routes refuse a workspace grant as well, because a harness run, an output folder and a chat handoff each belong to one project. So do the memories a user selects: a selection is stored per consent of one project, and `read_selected_context` is served by `GET /integrations/context` (not by the read-tool gateway, so it has no `project_id` selector and is not in `TOOL_SCOPES`) and takes its project from the grant; a workspace-bound context that reaches that service answers `context_unavailable`. `connect --workspace` therefore needs `--tools`, refuses `--publish`, `--chat`, `--handoff` and `--context`, and does not request `harness:execute`. `nous-harness run` and `workspace add` refuse a workspace connection and point to `--project`; `mcp install` still prints the standalone Codex command. Reconnecting with `--workspace` replaces the previous connection and does not carry registered local folders over, and the CLI says so. `request_action` refuses a workspace grant a note (422, `workspace connections cannot request this action`), because `create_project_note` cannot choose a project, and the bridge launches the MCP child without `--context` on a workspace connection even when the stored scopes claim `context:read`. A workspace connection holding `tools:write` still gets `--actions`, so `request_action` and `get_action_status` are offered for the library actions: made with `--write` but without `--library`, it asks for each one and the user approves each; with `--library` the reversible ones run at once.
- **Project selector.** On a workspace grant every tool that works on one project (the project-scoped tools under **Read tools**, and `list_project_artifacts`) advertises an optional `project_id`. The arXiv and connector tools, `get_arxiv_paper_content` and `list_library` act on no single project and advertise none; a caller that sends one gets 422 (unknown argument). It selects one project and is not identity. It must be a UUID and never a name (422 otherwise), and it must be one of the workspace's live Collections as `authorized_scope` computes them on that call (403 otherwise). Leaving it out returns the tool error `project_id_required`. A project grant still rejects `project_id` as an unknown argument (422), and every grant rejects `user_id`, `organization_id`, `thread_id`, `run_id` and `grant_id`.
- **`library:read`.** Adds `list_library`: one page of the folders (Collections) the grant may use, ordered by name, each with `id`, `name`, a description cut to 500 characters and its live `document_count`. `limit` is 1-50 (default 50) and `offset` starts at 0; `next_offset` is `null` on the last page. A page ends early when its names and descriptions would pass the 64 KiB result cap (it is measured in UTF-8 bytes, and 50 long CJK or emoji descriptions do), so it can hold fewer than `limit` folders: continue from `next_offset`, never from `offset + limit`. A project grant sees its one project. Folders follow workspace membership, not organization, like the rest of the workspace API (`workspace_access.py`): a user invited to another organization's workspace may hold a workspace grant, and `list_library` then names that workspace's folders, but counts only the grant organization's documents (the owning organization's are neither counted nor named), while every project tool refuses those folders because documents and everything behind a project are organization-scoped. `test_list_library_follows_membership_but_counts_documents_by_organization` pins this; do not add a `Workspace.organization_id` filter to `authorized_workspace`. `GET /api/v1/integrations/tools` lists only the tools a grant's scopes may call, and calling a tool outside them is refused with 403 even when the grant holds `tools:read`.
- **`library:write`.** Lets the six reversible library actions run without a per-action approval; a note, a folder deletion and an arXiv ingest still wait for one (see [Library actions](#library-actions)). `library:write` needs `library:read` and `tools:write`, and `library:read` needs `tools:read`; a consent request or grant missing one of them is refused with 403. `connect --library` asks for both library scopes. A connection that holds `library:write` also launches the MCP child with `--library` (beside the `--actions` its `tools:write` brings), which offers `request_action` and `get_action_status` on either binding.
- **Approval page.** `/integrations/approve` shows a **Workspace** row instead of **Project** for a workspace consent, and each scope as a plain-language label beside its raw name (`frontend/src/lib/integrations/scopeLabels.ts`). A scope without a label falls back to its raw name, so a label cannot hide a scope. The `library:write` label is the consent sentence quoted under [Library actions](#library-actions). The action review page names the workspace for an action that has no project (`create_folder`).
- **Rollback.** The migration's downgrade deletes every workspace-bound request and grant and every action without a project before it restores `project_id NOT NULL`, so rolling it back ends all workspace connections.

### Library actions

Plan 07 Slice 3 lets `request_action` change the user's library as well as add a note. `ALLOWED_ACTIONS` in `backend/src/services/agent/tool_actions.py` is the catalogue. Each action has its own argument validator (`validate_arguments`) and names its required scope (`REQUIRED_SCOPE_FOR`). **Auto-run** means the action runs inside the request when the grant holds `library:write`, and the reply carries its outcome. **Approval** means it waits as `awaiting_approval` until the requester approves it on `/integrations/actions/{invocation_id}`, then runs from the drain.

| Action | Arguments (`?` optional) | Required scope | Runs | Binding |
| --- | --- | --- | --- | --- |
| `save_papers_to_folder` | `document_ids`, `project_id` | `library:write` | auto-run | project or workspace |
| `remove_papers_from_folder` | `document_ids`, `project_id` | `library:write` | auto-run | project or workspace |
| `move_papers_between_folders` | `document_ids`, `from_project_id`, `to_project_id` | `library:write` | auto-run | workspace only |
| `create_folder` | `name`, `description`? | `library:write` | auto-run | workspace only |
| `rename_folder` | `project_id`, `name` | `library:write` | auto-run | project or workspace |
| `update_document_metadata` | `document_id`, `title` and/or `tags` | `library:write` | auto-run | project or workspace |
| `delete_folder` | `project_id` | `tools:write` | approval | project or workspace |
| `ingest_arxiv_papers` | `paper_ids`, `project_id`? (required on a workspace) | `tools:write` | approval | project or workspace |
| `create_project_note` | `title`, `content`, `tags`? | `tools:write` | approval | project only |

`tools:write` may request every action, but a grant without `library:write` gets approval for every one of them, the auto-run ones included.

- **Consent sentence.** The `library:write` label reads: "Add, remove, move and rename items in this workspace, and change the title and tags of a paper in it (including removing every tag), without asking each time. An edited paper changes everywhere it appears. Deleting folders and ingesting papers still require your approval." The approval page shows it beside the raw scope name (`frontend/src/lib/integrations/scopeLabels.ts`, checked by `scopeLabels.test.ts` and `IntegrationApprovalPage.test.tsx`). The paper edit is `update_document_metadata`, which changes the document itself, so its new title or tags show in every folder that holds it. On a project connection the same changes reach that one project only (no new folders, no moves).
- **Which scope may ask.** `scope_allows` lets `tools:write` request any action and `library:write` only the six it auto-runs. The routes admit a grant that holds either scope, for requests and status reads alike (`require_integration_context_any` in `backend/src/api/integrations/auth.py`), and `request_action` then checks the action's own scope: a scope that does not cover it is 403. Before anything runs, `_authority_intact` checks the same per-action scope again on the grant and on its consent. `library:write` needs `tools:write` (`_SCOPE_REQUIRES` in `backend/src/services/integrations/context.py`), so a grant holding it can still request a deletion, an ingest or, on a project, a note, each for approval. `test_library_write_alone_cannot_request_a_note_a_deletion_or_an_ingest` and `test_library_write_alone_cannot_execute_a_deletion_or_an_ingest` pin the per-action check for a grant that would hold `library:write` without `tools:write`.
- **What runs at once.** An action in `AUTO_RUN_ACTIONS` requested under `library:write` (`runs_without_approval`) is stored already approved, with the requester recorded as the decider: the user's consent to `library:write` stands in for the per-action decision. `request_action` commits that row, then claims and runs it in the same request through the claim the drain uses (`_execute_row`), and replies with the outcome (`succeeded` or `failed`, with the receipt) instead of an approval link. If the drain claims the row first, the reply reports the row's state at that moment. Auto-run skips only the decision: the target check, the authority re-check and the single transaction are the same on both paths. Every other request is stored `awaiting_approval` and runs from the drain once approved.
- **Arguments and targets.** No action accepts an identity argument (`user_id`, `organization_id`, `workspace_id`, `thread_id`, `run_id`, `grant_id` or `consent_id`; 422). Only the selectors `project_id`, `from_project_id` and `to_project_id` choose a folder. They must be UUIDs, never names (422), and `_resolve_target` checks them against the grant's live scope (`authorized_scope_filter`) before a row is stored: anything out of scope is 403, and a folder outside the grant reads like a missing one. A project grant reaches its own project only, so it can neither create a folder nor move papers (403). A workspace grant may name any live Collection of its workspace that the user can still reach. `create_folder` aims at the workspace itself. `update_document_metadata` takes no selector: its target is the first folder by name, within the grant's scope, that holds the document, which must be a live document of the grant's organization (403 when no such folder exists), and its receipt lists every such folder in `project_ids`. `ingest_arxiv_papers` must name its folder on a workspace grant (422, `project_id is required`); a project grant may name only its own. When the action runs, `_target_reason` repeats the live check for either binding before the effect: the project or workspace must not be deleted, the user must still own the workspace or be a live member, and the user and both organizations must be active, or the action fails with `grant no longer authorizes this action` (`test_a_project_bound_action_rechecks_live_access_when_it_runs`). A requester who is no longer active, or has left the organization, is refused before that check, with `requesting user is not active` or `requesting user left the organization`. `document_ids` takes 1-20 ids and `paper_ids` 1-10 arXiv ids, none repeated; a name or title is 1-255 characters, a description at most 2,000, and `tags` at most 20 of 1-64 characters (`[]` clears a paper's tags).
- **Move.** `move_papers_between_folders` is unlink + link in one transaction. `_move_papers` removes the papers from `from_project_id` and adds them to `to_project_id` in the transaction that also writes the receipt, so a failure in either half rolls back both, and a paper never leaves the source without joining the destination (`test_move_is_atomic`). Only papers that are live members of the source move; the rest are listed in `skipped_document_ids`. If a paper leaves the source but cannot join the destination (a deleted document, say), the move fails with `target not found` and nothing changes. When it runs, the destination is re-checked against the workspace like the source (`test_move_destination_is_rechecked_when_it_runs`).
- **Effects and receipts.** Every action except the ingest runs its effect and writes its receipt in one transaction (`_run_effect`, committed by `_finish`). The collection services only flush, and `update_document_metadata` calls `update_file_metadata(..., commit=False)` in `backend/src/services/documents/file_metadata_service.py`, the service that `PUT /api/v1/files/{file_id}` now uses as well. The services act as the requesting user: changing a folder needs edit rights on its workspace, and editing a paper needs the requester to be its uploader or an admin, as the files route does (`insufficient permissions` otherwise). Removing papers and deleting a folder keep the documents, and a deleted folder is soft-deleted. A receipt holds fixed fields, never a service's own text: `ok`, `tool_name` and `project_id` (for `create_folder`, the new folder), plus the action's own fields (the papers' `document_ids`, with `skipped_document_ids` for a save, removal or move; a move's `from_project_id` and `to_project_id`; a new folder's `workspace_id` and `name`; a rename's `name`; an edit's `project_ids`, the `title` or `tags` it set, and the `previous_title` or `previous_tags` it replaced, so asking for those values again undoes it). A failed action records a stable reason (`target not found`, `insufficient permissions`, `grant no longer authorizes this action`, `consent revoked`, `effect failed before commit` and others) and changes nothing.
- **arXiv ingest.** `ingest_arxiv_papers` never auto-runs and never shares the receipt's transaction (`DETACHED_ACTIONS`), because the ingest stores each paper and saves it to the folder through sessions of its own and object storage. Once approved, the drain claims it like any action (the committed claim is its idempotency key: one worker starts it and nothing re-runs it), re-checks authority, ends that read transaction and runs the ingest; the receipt is written afterwards. Its atomicity is therefore weaker, and the receipt's `atomicity` field says so: papers that landed stay in the library even when the action reports a failure. The receipt lists `paper_ids`, the `document_ids` created, `failed_paper_ids`, `ingest_status` and `linked`, which is true only when the ingest reports the action's folder as the one it saved them to. A partial ingest, papers stored but not saved to the folder, and a failed ingest each end `failed` with a stable reason. Stored papers that were not saved to the folder always read `papers ingested but not saved to the folder`, a partial ingest included, whose `ingest_status` stays `ingestion_partial`; an ingest that raises ends `outcome_unknown` (`ingest outcome unknown`). The ingest runs inside the drain's Celery task for at most `DETACHED_TIMEOUT` (120 s, the agent graph's bound for the same tool); one that runs longer is cancelled and ends `outcome_unknown` the same way. The rows of one drain run one after another, so a drain spends at most `DRAIN_BUDGET` (240 s) starting them and starts an ingest only while the whole timeout still fits; an ingest it skips stays approved, unclaimed, for a later drain. The drain task's own limits (`soft_time_limit=300`, `time_limit=360` in `backend/src/tasks/integration_action_tasks.py`) sit above that budget. If the drain is cancelled anyway, at its soft time limit or on a worker shutdown, the ingest it was running is recorded `outcome_unknown` before the cancellation goes on. When `SWEEPERS_ENABLED` is on, `sweep_stale_actions` still moves a row left `executing` for 5 minutes (a worker that died outright) to `outcome_unknown`, and a late receipt is discarded; papers that landed stay in every case.
- **Review page.** `/integrations/actions/{invocation_id}` (`frontend/src/components/integrations/IntegrationActionApproval.tsx`) leads with `ActionReview.summary`, one sentence from a template per action (for example `Delete folder “Reading” (documents are kept)`), then lists the stored `arguments` under their raw keys, so nothing the sentence leaves out is hidden; a note keeps its title, tags and content. The summary names a folder only inside the action's own workspace, and a paper only when it is a live document of the requester's organization. Any other id stays an id, so a request cannot make the page read out another organization's titles. A change aimed at a folder that has since been deleted can be denied but not approved.
- **Bridge.** `request_action` advertises the nine actions with their fields and sends each with only its own (`ACTION_FIELDS` in `packages/harness-bridge/src/actions/mcp.ts`), refusing a malformed field before any request. A null `description` (`create_folder`) or `project_id` (`ingest_arxiv_papers`) is dropped, because NOUS reads null there as left out; any other null is refused, as NOUS refuses it (`tags: []` clears a paper's tags, `tags: null` does not). It calls only `succeeded` done (`Done.`); `awaiting_approval` reads `Not done yet.` with the approval link, and `failed` reads `Not done:` with the receipt. The [package README](../../packages/harness-bridge/README.md#note-and-library-actions) lists the actions for users.
- **Tests.** On SQLite, `backend/tests/unit/services/agent/test_tool_actions.py` covers the catalogue and validators, the per-action scope on request and on execution, identity refused and selectors checked against the live scope, auto-run under `library:write` and approval otherwise, `test_move_is_atomic`, the re-checks of a move's destination and of `create_folder`'s workspace when they run, the ingest through the drain and its stable outcomes, its timeout, a drain cancelled mid-ingest and the drain's budget, and what the review may name. `backend/tests/unit/api/test_integration_actions.py` covers the routes' scope admission and their stable 403. `backend/tests/unit/services/test_file_metadata_service.py`, `backend/tests/api/documents/test_files_update_metadata.py` and `backend/tests/unit/architecture/test_document_file_boundaries.py` cover the extracted metadata service, the route's unchanged HTTP behaviour and a handler with no transaction calls. The Vitest suite `frontend/src/components/integrations/__tests__/IntegrationActionApproval.test.tsx` covers the review page, and `packages/harness-bridge/test/actions.test.ts` the fields sent per action, the local refusals and `--library` offering the action tools. An auto-run or drain claim under concurrent PostgreSQL workers, an ingest on a real worker, and any library action against a deployment are **NOT RUN**.

## Consent, disclosure, and isolation limits

Consent is separate from CLI login: the browser authorizes the CLI user, then an authenticated browser approves the device grant for one project or, for a workspace connection, one workspace. `nous-harness disconnect` revokes this device's access. It renews its stored grant if needed and calls `DELETE /api/v1/integrations/grants/{grant_id}` with the CLI token and that grant. That call revokes the grant and the consent it was exchanged from, so the grant cannot be renewed and approved actions under that consent no longer execute. After the revocation commits it also moves the owner's CLI revoked-before cutoff, described below. The command then removes the local credentials. If NOUS cannot be reached or returns a server error while the stored grant is less than 15 minutes old, nothing is removed and the command can be retried.

The route sets `end_cli_sessions` on `revoke_integration_grant` only for a CLI-token caller, so revoking a grant from a browser session leaves CLI logins alone. CLI tokens carry no device ID, so the cutoff is per user: **every CLI login of that user ends, not only this computer's, and the other computers must run `nous-harness connect` again.** A computer whose login ended this way is refused (401) when it tries to revoke, so its own `disconnect` only removes its local credentials and its consent stays valid. The cutoff is a best-effort Redis write. If Redis is unreachable the write is skipped without a retry, the server only logs a warning, the DELETE still returns 204, the command still reports success, and the CLI login stays valid until it expires (30 days by default). `CLI_TOKEN_REVOCATION_FAIL_CLOSED` only governs how reads treat an unreachable store.

`disconnect` cannot revoke anything once the stored grant has expired, because an expired grant can be neither renewed nor used to authorize the revoke call. The grant ages from `connect` or its last renewal, so a bridge that has been stopped for more than 15 minutes lands here. If renewal is refused, or NOUS is unreachable or returns a server error for a grant that old, `GrantKeeper` raises `GrantExpired` and `disconnect` removes the local credentials. It does the same when NOUS refuses the revoke call itself (401, 403 or 404) and for a connection made before grant renewal shipped, which has no stored grant ID. In each case the command prints a pointer to `/integrations/devices` and **neither revokes the consent nor ends the CLI login.** The grant itself lapses within 15 minutes of its last renewal, but the consent stays valid until it is revoked another way, and approved actions under it still execute, because the executor re-checks the consent and not the grant token. To be sure the consent is revoked, run `disconnect` while `nous-harness run` is still running or within 15 minutes of the last renewal.

The browser page `/integrations/devices`, linked from **Settings → Connected devices**, lists the signed-in owner's devices through `GET /api/v1/integrations/connections`. Project labels and access appear only while the user remains authorized for a live project, workspace, and organization. Expired unexchanged approvals are hidden; consumed consents remain visible after their original exchange window expires. Each device shows its stable ID and connection time to distinguish repeated labels.

The browser can revoke one consent through `POST /api/v1/integrations/grant-requests/{request_id}/revoke`, which ends that consent and every grant issued under it, or disconnect a device through `POST /api/v1/integrations/devices/{device_id}/revoke`, which ends that device and all its consents and grants. These routes require an interactive browser session and enforce owner/organization checks. Browser device disconnect also ends **all existing CLI sign-ins for the account**, because CLI tokens have no device identity; the browser asks for confirmation with that consequence. Other devices' integration grants remain active, but their CLI must sign in again. Unlike the best-effort CLI DELETE above, browser disconnect requires a confirmed shared Redis cutoff before committing the device revocation. If that write fails, the database changes roll back and the route returns a safe, retryable 503. The cutoff includes CLI tokens issued in the same second and is shared across API instances.

Deleting local state without `disconnect` stops this bridge instance but does not revoke the server grant; the browser page remains available to revoke that device's access. Revocation prevents further grant-authorized work, but does not itself terminate a native process already accepted by Codex. The local CLI state uses owner-only permissions and stores access/grant credentials behind an opaque handle.

NOUS persists the accepted user message, assistant text deltas, tool lifecycle summaries, usage, native approval targets, and terminal events in its chat/run records. Codex receives the prompt and executes local work. Keep secrets out of prompts and workspace output unless they are intended to be processed by both systems. The browser receives IDs and labels, not local absolute workspace paths or CLI grant tokens.

The app-server start/resume policy is checked against the configured workspace-write sandbox, writable roots, approval policy, reviewer, and network setting. This does **not** provide a folder-only read guarantee: registering a root identifies the requested write scope; it is not proof that Codex cannot read files outside that root. The feature treats the local computer and data available to the Codex process as trusted execution context. Optional MCP configuration is locally composed and session-scoped, never supplied by the browser.

Command requests support one-time allow/deny. File-change requests stay deny-only until the persisted backend request schema carries a disclosed path or concrete change summary. An item ID or generic reason is insufficient review context. Unknown request shapes, persistent grants, changed approval targets, expired/revoked grants, and stale decisions fail closed.

## Recovery and operational controls

The local journal records native command intent before sending it. If acceptance or an interrupt is ambiguous, the bridge does not replay that action and retains the workspace lock while it reconciles exact Codex history. An unmatched or unverifiable native action remains quarantined; restarting the bridge with the same state allows reconciliation to continue. Do not remove the journal, clear the lock manually, or treat a WebSocket close/interrupt receipt as proof that Codex stopped.

**A run NOUS refuses.** The socket re-checks the device grant on every frame. It checks each event against its own run's authority: the run's chat, that chat's project link, the folder binding, the user's access, and the consent the run was started under.

When the grant is valid but that run's authority is gone (for example, its chat was deleted or linked to another project, or its folder registration was removed), NOUS writes nothing for that event and answers it with `{"reject": {"runId", "sourceId", "sourceSeq", "generation", "code": "run_access_denied"}}` instead of closing the socket. It sends the same reply for an event it cannot match to its run, such as an unknown run, command or approval record or, for an output event or observation, a device, folder or generation mismatch, so the code does not always mean that access was lost. NOUS re-checks the grant before it replies. A token revoked mid-frame, by a renewal or a disconnect, therefore still closes the socket with 4403, like any other grant-level failure.

The bridge marks the run `denied` in its journal and prints one notice for it. It drops the run's unsent events, journals nothing more for it, and keeps uploading the device's other runs. Closing the socket instead stalled the whole device: the bridge re-sends its oldest unacknowledged event first on every reconnect, and each reconnect journaled the refused run again. A refusal is final for that run, even if its access later returns.

A reject does not prove that NOUS stored nothing for the run. NOUS authorizes an event before it looks up the event's receipt, so it also refuses the replay of an event it had already stored. Unless NOUS had already stored the run's terminal observation, it keeps the run open and its workspace locked, and a new run in that folder fails with "A response already owns this local workspace." If it had, its reconcile pass may still finalize the run and unlock the folder on the server.

On the bridge, the outcome depends on whether the run finished on this computer, and the notice says which case applies. If the run's terminal observation is already journaled but not yet acknowledged, Codex has stopped writing, so the bridge releases its local lock. Otherwise the reject is not terminal evidence: the bridge keeps its local lock and stops renewing the run's lease, even while NOUS still offers one, so the lease watchdog interrupts the native turn once the lease lapses, also after a restart. While either lock remains, the folder stays reserved on that computer.

To free the folder, run `disconnect`, `connect` and `workspace add` again, which registers it under a new ID. `connect` with the same options would reuse the stored binding, and `workspace add` alone returns the folder's existing ID. After `disconnect` the stored binding is gone, so `connect` needs its original flags again (`--api`, `--project` and `--label`, plus any `--chat` or scope flags such as `--tools`), and the new computer entry and folder must be selected in the chat composer. `disconnect` revokes this device's grant and also ends your CLI sign-ins on other computers. This device's other runs stop too: their leases lapse, their turns are interrupted, and their events, now from a new device, are refused, so their chats stay in progress. Let other runs finish or stop them first.

A bridge older than this change treats the reject frame as invalid and reconnects, so one refused run still stalls it: update the bridge together with the backend.

`backend/tests/unit/services/harness/test_delivery.py` (`-k "denied_run or grant_lost"`) and `packages/harness-bridge/test/denied-run.test.ts` cover this. Live acceptance is **NOT RUN**.

For an uncertain interrupt that still cannot reconcile, stop the bridge and run:

```sh
pnpm --filter @nous/harness-bridge start recover-interrupt
```

The command lists exact interrupt command IDs. Recovery is permitted only with verified boot identity on the same macOS/Linux computer. If a legacy record has no baseline, the first invocation records one; wait at least ten seconds, reboot that same computer, then run:

```sh
pnpm --filter @nous/harness-bridge start recover-interrupt --command COMMAND_UUID
```

Recovery removes only that interrupt's uncertain-delivery blocker. It preserves run outcome and workspace ownership; restart the bridge so normal reconciliation can supply terminal evidence. Same-boot, different-machine, or unavailable OS evidence is rejected. Do not edit the SQLite journal by hand.

`HARNESS_BRIDGE_ENABLED` is the backend kill switch and defaults to `false`. Setting it to `false` rejects newly accepted Codex chat work and prevents pending start commands from dispatching. Reads, cancellation, and reconciliation of already accepted runs remain available to bring work to a known state. After disabling the feature, monitor outstanding runs until they have terminal outcomes before retiring their paired device.

## Conformance and live acceptance

The package conformance test verifies that every capability an adapter advertises has a corresponding callable operation. The pinned Codex fixture tests exercise the app-server protocol and policy checks; the conformance helper alone does not prove a Codex binary or remote service is available. Additional adapters remain gated until conformance and their operation-specific fixture contract tests pass.

The Playwright live acceptance is opt-in and uses a dedicated, project-bound test thread and workspace on a real paired device running the bridge. It asks Codex to execute a unique marker-file command that writes outside the registered workspace root (an in-root write runs inside the workspace-write sandbox and never raises an approval, so it cannot exercise this path); it expects an exact command-approval request, reloads the chat while the request is pending, approves once, and verifies the persisted user/assistant marker appears only once after completion and another reload. It annotates the NOUS thread and accepted run IDs. It intentionally does not expose or log local credential material. The native Codex session ID is not exposed to the browser and is not claimed by this test.

Run this live test on the paired computer, with a disposable workspace root that excludes the home directory, so the unique out-of-root marker and its `finally` cleanup refer to the same local filesystem.

Configure `NOUS_HARNESS_E2E=1`, `NOUS_HARNESS_E2E_DEVICE_ID`, `NOUS_HARNESS_E2E_WORKSPACE_ID`, `NOUS_HARNESS_E2E_THREAD_ID`, `NOUS_HARNESS_E2E_EMAIL`, and `NOUS_HARNESS_E2E_PASSWORD` to enable the live scenario. The named workspace must point to a disposable local test fixture, the thread must be bound to the same NOUS project, the device bridge must be running, and the backend kill switch must be enabled. Without opt-in/device/credentials the test reports **skipped / NOT RUN** with the missing prerequisite in its reason. Skipped is never counted as live acceptance. Report local fixture tests, hosted CI job/SHA, and live-device outcome separately; for live runs include the NOUS thread and run IDs recorded in Playwright annotations. CI without those dedicated secrets and a connected device has no live result.

From the repository root, run the focused conformance suite with:

```sh
pnpm --filter @nous/harness-bridge test -- test/conformance.test.ts
```

Run the separately configured browser acceptance with:
