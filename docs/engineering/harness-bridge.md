# Local Codex harness bridge

**Status:** Implemented as a local Codex bridge feature; live acceptance requires a deliberately configured NOUS test project, paired device, and workspace, and has **NOT RUN** against a deployment. This document describes the current bridge contract. It does not cover cross-chat context synchronization or tracing. Through the opt-in local stdio MCP facade described in [NOUS read tools over MCP](#nous-read-tools-over-mcp), Codex can call NOUS read tools, publish one file from a registered workspace root as a NOUS artifact, and request a project note that the user must approve in the browser, each only under a scope the user approved. Selecting project memories to share (`context:read`), artifact editing and artifact sharing are not exposed. A connection can instead be bound to one NOUS workspace (MCP-only) and can request `library:read` and `library:write`; only `library:read` has any effect yet. See [Workspace connections and library scopes](#workspace-connections-and-library-scopes).

## User workflow

1. An owner runs `nous-harness connect` on the computer that will execute Codex. The CLI completes NOUS browser authorization, registers the device, and waits for browser consent to a project-scoped `harness:execute` grant.
2. The owner registers a local workspace root, starts `nous-harness run`, and selects **Local Codex**, the paired computer, and its workspace in the NOUS chat composer.
3. NOUS durably accepts the chat message and run before dispatch. The local bridge receives a fenced command over authenticated WSS and starts the pinned Codex app-server with the verified local policy. Persisted events flow back to the existing chat transcript.
4. Exact, one-time Codex command approvals and required input are shown in NOUS. The browser re-reads the saved request before a decision and sends only the decision plus the displayed target hash. The local CLI grant token never enters the browser.
5. If the browser disconnects, execution continues and NOUS can replay persisted events when the chat reconnects. Browser presence is not run ownership or terminal evidence.

NOUS-native chat remains the default provider. Provider/device/workspace selection is scoped to the signed-in user and chat thread. The bridge does not search or continue other NOUS conversations or synchronize a context file. Codex reaches NOUS only through the opt-in MCP facade below, and only with the scopes approved for this device.

## NOUS read tools over MCP

`nous-harness mcp` is a local stdio MCP server (`packages/harness-bridge/src/mcp/`) that forwards `tools/list` and `tools/call` to the backend read gateway (`GET/POST /api/v1/integrations/tools[/read]`, gated by `NOUS_MCP_ENABLED`, default `false`). The backend owns the tool allowlist, JSON Schema catalog, argument validation, project scoping, and result bounds; the facade adds nothing a caller could use to widen them.

- **Read tools.** The catalog carries two kinds of tool. Project-scoped tools resolve the Collection from the grant, never from arguments (a workspace grant names it with the validated `project_id` selector, see [Workspace connections and library scopes](#workspace-connections-and-library-scopes)), and return `requested_documents_unavailable` for any document outside it (a foreign id and an unknown id are indistinguishable): `search_documents`, `list_project_documents`, `do_kb_retrieve`, `get_current_draft`, `get_document_content` (summary or full text, paginated by characters with `offset`/`limit` ≤ 48,000 and a `next_offset` to follow until it is `null`) and `retrieve_passages` (PostgreSQL full-text ranking over the project's documents, `document_ids` optional, `top_k` ≤ 20; the `answer_pdf_queries` analog that works with `DO_KB_ENABLED=false`), `find_researchers` and `get_researcher` (see **Researcher tools** below). Args-only tools take no identity and are dispatched before the project check: `search_arxiv` (120 s budget shared with the agent's slow tier, at most 20 results advertised, arXiv itself returns up to 5), `search_external_database` and `list_external_databases` (connector registry, at most 20 results), and `get_arxiv_paper_content` (full text of one arXiv id, paginated like `get_document_content`, cached in Redis: 24 h fresh, up to 7 d stale fallback when a refetch fails). `get_arxiv_paper_content` persists nothing; use `ingest_arxiv_papers` to add a paper to NOUS. `list_library` (scope `library:read`) acts on no single project either: it lists the folders of the grant's whole scope. Every result is capped at 64 KiB; upstream failures come back as stable tool errors (`upstream_timeout`, `upstream_unavailable`, `arxiv_unavailable`, `retrieval_unavailable`, `researcher_not_found`) and never carry exception text. `source_refs` list only observed identities: `document_id`, `draft_id`, `arxiv_id`, or `external_id` with its `connector`.
- **Researcher tools.** `find_researchers` (`query` 1-200 characters, `limit` ≤ 25, default 10) returns `{researchers: [{researcher_id, name, paper_count}]}` and `get_researcher` (`researcher_id`) returns `{researcher: {researcher_id, name}, papers: [{document_id, title, arxiv_id?, published?}], coauthors: [{researcher_id, name, paper_count}]}`, with `source_refs` of one `document_id` per listed paper (`find_researchers` returns none). Both read one source: `Document.document_metadata["authors"]`, the author list that arXiv ingest persists, of the live documents of the grant's project, or of the one a workspace grant selects (the same project-and-ancestors join as every other project-scoped tool). **Coverage is the author lists of papers ingested into that project.** Documents without an author list are invisible. NOUS stores no affiliations, institutions or career history for them, and the tools do not claim any. Because the index is the project's own documents, another project's papers and authors in the same organization can never appear, and an author who only wrote for another project answers `researcher_not_found`, the same as an unknown id. (The knowledge graph's `PERSON` entities are not used: the graph is scoped by organization only and carries no document ids, so it cannot be restricted to a project.) A `researcher_id` is the author's name casefolded with whitespace collapsed (at most 200 characters), so spelling variants merge and `name` is the newest document's spelling; two different people with the same name are one researcher. `find_researchers` matches the query as a case-insensitive substring and orders by paper count, then `researcher_id`. `get_researcher` lists at most 100 papers (newest `publication_date`/`published` first, then newest ingest) and at most 100 co-authors, counted over every paper of the researcher, not only the listed ones. The tools scan the 2,000 newest documents of the project in Python (O(documents × authors)); when a list is cut, by that scan window, `find_researchers`'s `limit`, the 100-item caps or the 64 KiB result cap (measured over the whole response, `source_refs` included), the payload carries `truncated: true`. When the scan window hid older documents, a `researcher_not_found` from `get_researcher` also carries `truncated: true` (still an error): the author may exist in a document that was not scanned. Live proof (ingest an arXiv paper into a dev project, then call both tools) has **NOT RUN**; the tests use SQLite project and document fixtures only.
- **Consent.** `nous-harness connect --tools` requests `harness:execute` plus `tools:read`; adding `--publish` also requests `artifacts:publish`, adding `--write` also requests `tools:write`, and adding `--library` (which also needs `--write`) requests `library:read` and `library:write`. `--publish`, `--write` and `--library` are refused without `--tools`. `--workspace WORKSPACE_UUID` replaces `--project` and binds the grant to a workspace instead of one project (see [Workspace connections and library scopes](#workspace-connections-and-library-scopes)). Every scope appears on the browser approval page, with a plain-language label beside its raw name. `tools:read` covers the whole read catalog above except `list_library` (`library:read`), including the arXiv and external-connector searches, which leave NOUS to query third-party services with the model-supplied query. A connection made without `--tools` has no MCP access and `mcp install` refuses with a reconnect hint. The stored scopes only decide whether the local process offers a tool; the backend re-checks the grant on every request.
- **Managed sessions.** When the local connection carries `tools:read`, `nous-harness run` adds a session-scoped `mcpConfig` entry that launches `nous-harness mcp --api ORIGIN --store DIR --session HANDLE` for that Codex thread. Argv contains only the API origin, the state directory, and the opaque credential handle; the CLI JWT and grant token are read from the owner-only store inside the child.
- **Standalone Codex.** `nous-harness mcp install` prints the `codex mcp add nous -- …` command for the user to run. The package never edits `~/.codex/config.toml` or any other global Codex configuration.
- **Transport hygiene.** Stdout is the JSON-RPC channel; diagnostics go to stderr. The API origin must be HTTPS, except the explicit loopback development hosts. Model-supplied arguments are sent only inside the invocation body; they cannot set headers, URLs, identity, or credentials. Gateway rejections are stable tool errors with no retry: 401 → reconnect with `--tools`; 403 → the grant lacks the scope of that tool (`tools:read`, or `library:read` for `list_library`) or the resource is outside the granted project or workspace (the bridge's message text still names only `tools:read` and the project); 422 → the gateway's own argument reason; 503 → NOUS's own reason (tools disabled, artifact publication disabled, or artifact storage unavailable). Network failures name the URL and the underlying cause on stderr. `run` logs a stderr notice when the connection has no `tools:read`, so a missing `nous` server is never silent.
- **Publication.** When the connection carries `artifacts:publish` (`connect --tools --publish`), managed sessions launch the MCP child with `--root <registered workspace root>` and the server offers `artifacts_publish` (`packages/harness-bridge/src/artifacts/`). Each call validates the relative path lexically, refuses symlinked or hard-linked files, then opens the file with containment enforced on the descriptor rather than the path string: macOS uses `O_NOFOLLOW_ANY` so the kernel refuses a symlink in any component (a directory swapped for a symlink after the path checks fails with `ELOOP`), Linux checks the opened descriptor's real path under `/proc/self/fd` against the root, and other platforms are refused. Size is compared before and after the open and the read is bounded to the validated size. The bytes are then reserved, uploaded and finalized through `/api/v1/artifacts` with the grant headers; the backend re-verifies size, digest and scope, and serves downloads as attachments with `nosniff`. Publication is gated by `ARTIFACTS_ENABLED` (default `false`), not by `NOUS_MCP_ENABLED`: with it off, reserve, upload and finalize answer 503 "Artifact publication is disabled". `mcp install` binds the single registered root, or the one named with `--root`; several registered roots require an explicit choice. A root that no longer exists at launch is logged to stderr and publication is simply not offered; read tools keep working. **The root is a publish scope, not a read boundary:** under Codex `workspace-write` the model can copy any file it can read into the root and publish it, exactly as it could write it to disk. That matches Plan 01's stated limit that folder registration is not read isolation. A workspace-bound grant cannot publish: the artifact routes answer 403.
- **Note requests.** When the connection carries `tools:write` (`connect --tools --write`), managed sessions launch the MCP child with `--actions` and the server also offers `request_action` and `get_action_status` (`packages/harness-bridge/src/actions/`). `request_action` supports only `action=create_project_note` with a client-generated UUID `invocation_id`, a title (at most 255 characters), Markdown content (at most 200,000 characters) and up to 20 tags; identity and project come from the grant, never from arguments. It calls `POST /api/v1/integrations/actions`, which records the request idempotently by invocation ID and payload and returns `awaiting_approval` with an `approval_url` for the browser page `/integrations/actions/{invocation_id}`. Nothing is created until the signed-in requester opens that page, reviews the stored title, content and project, and approves. The decision route (`POST /api/v1/integrations/actions/{invocation_id}/decision`) refuses every CLI token, so a harness cannot approve its own request. The `drain_integration_actions` beat task (every 2 s) claims each approved row with a conditional update, re-checks authority against the consent the grant was exchanged from rather than the short-lived grant token, and then creates the note and its receipt in one transaction. A commit with an ambiguous outcome leaves the row `executing`. When `SWEEPERS_ENABLED` is on, `sweep_stale_actions` moves such rows to `outcome_unknown`, and they are never re-run. `get_action_status` reports `awaiting_approval`, `approved`, `executing`, `succeeded`, `failed` (including a denial) or `outcome_unknown`. `NOUS_MCP_ENABLED=false` rejects new requests and holds approved rows unexecuted, while status reads of existing requests keep working. The backend guard lives in `backend/src/services/agent/tool_actions.py`. A workspace-bound grant cannot request a note: `request_action` answers 422.
- **Grant renewal.** Integration grants live 15 minutes. The bridge and each MCP child share one credential handle and keep it fresh with `GrantKeeper` (`packages/harness-bridge/src/grants.ts`). Once the stored grant is 10 minutes old, it renews through `POST /api/v1/integrations/grants/{grant_id}/renew`. Long-running processes check every 2 minutes, and the replacement is written back to the owner-only store so other processes pick it up. Renewal revokes the old grant token and issues a new one with the same consent, binding (project or workspace) and scopes. It cannot widen scopes or revive an expired, revoked or consent-revoked grant. A publish sequence (reserve, upload, finalize) is pinned to one grant and starts only on a grant at most 5 minutes old. Connections made before renewal shipped have no stored grant ID, so they stop after 15 minutes and must reconnect.
- **Binding reuse.** `connect` reuses the stored connection, with no `/cli-auth/start` and no consent, only when all of these hold: a stored connection exists, `apiBase(apiUrl)` is unchanged, the project or workspace and `threadId` match (both absent counts as equal; a project and a workspace are different bindings), the stored scopes include every requested scope, and a forced `GrantKeeper.current(0)` renewal issues a new grant token. A transient renewal failure keeps the old token, so it does not count as proof. Otherwise the full flow runs. After a reconnect to a different chat, project or workspace is stored, the superseded credential handle is deleted locally. **Known gap:** the superseded server grant and consent are not revoked until `disconnect` (the grant lapses within 15 minutes; the consent does not). The probe forces a grant renewal, which revokes the previous grant token; running MCP children recover on their next call, but do not reconnect during an active publish sequence. `nous-harness status` reports the project and chat, or the workspace, device label, grant expiry (stored `renewedAt` + 15 minutes) and queue counts offline.
- **Handoff queue.** `handoff show|save|flush|list|discard` (`src/cli.ts`) and `save_nous_handoff` share `src/handoffs/queue.ts`. Each save is journaled as `handoff-<handoff_id>.json` (owner-only, through `CredentialStore`) before the POST, then deleted on 2xx, kept as `pending` on a network error, timeout, 5xx, 429, 401 or `GrantExpired` (with a reconnect hint for the last two), as `conflicted` with the 409 latest version (never merged), or as `rejected` on 403, 422 or another 4xx. `flush` is manual and has no daemon. It re-sends `pending` entries whose `thread_id`/`project_id` match the current binding with the same `handoff_id`, so the backend dedupes, and reports others as skipped. `handoff discard ID` removes one entry in any state and prints it. The MCP child journals only when `connection.json`'s `credentialHandle` equals its session handle, so a stale child cannot journal under, and later flush into, a newer chat binding. A pending MCP save names the queued `handoff_id`. A workspace connection has no chat, so the handoff commands refuse it. `handoff save` and `handoff flush` are intended hook targets; Codex hooks are **not wired** in v1 because per-harness hook support is unverified. Add a background retry only if pending entries are seen to accumulate.
- **Tests.** `packages/harness-bridge/test/mcp.test.ts` spawns both the managed configuration and the standalone command against a recording HTTP server and asserts identical `source_refs`, correct grant headers, JSON-RPC-only stdout, no secrets in the config or install command, and no writes under `CODEX_HOME`. `test/actions.test.ts`, `test/grants.test.ts`, `test/disconnect.test.ts`, `test/connect-reuse.test.ts` and `test/handoff-queue.test.ts` cover note requests, renewal, disconnect, binding reuse and the handoff queue against stubbed HTTP responses. The backend action tests run on SQLite, so the conditional row claim under concurrent PostgreSQL workers is **NOT RUN**. Live acceptance against a real Codex and NOUS deployment is **NOT RUN** by these suites. Workspace scope resolution, the project selector and `list_library` are covered on SQLite by `backend/tests/unit/services/integrations/test_context.py` and `test_read_tools.py`; catalog filtering and per-tool scope refusal over HTTP by `backend/tests/unit/api/test_integration_tools.py`; the refusal of workspace grants by the harness socket, the artifact routes and `request_action` by `backend/tests/unit/api/test_harness_workspace_guard.py`, `test_artifacts_api.py` and `backend/tests/unit/services/agent/test_tool_actions.py`; the `--workspace` and `--library` flags by `packages/harness-bridge/test/mcp.test.ts`, and workspace binding reuse, `status` and the handoff refusal by `test/connect-reuse.test.ts`; and the approval page by the Vitest suites `frontend/src/lib/integrations/__tests__/scopeLabels.test.ts` and `frontend/src/components/integrations/__tests__/IntegrationApprovalPage.test.tsx`. The binding CHECK constraints are exercised on SQLite through the model metadata, not through the migration, and no unit test runs `hb03_workspace_grants`: `scripts/ci/check_alembic.py` only checks it for a single Alembic head and revision-id length. It was run by hand on a scratch PostgreSQL 14 on 2026-10-06: `alembic upgrade head` from an empty database, a downgrade and a second upgrade, and, against a minimal pre-hb03 schema, the CHECK constraints refused rows with neither binding and request or grant rows with both (an action may carry both) while the downgrade deleted the workspace-bound rows and restored `NOT NULL`. Its downgrade over production-shaped data and a deployed upgrade are **NOT RUN**.

### Workspace connections and library scopes

Plan 07 Slice 1 lets a grant bind one NOUS workspace instead of one project, and adds the `library:read` and `library:write` scopes. This section describes what the code does today. The approved design, including the library actions that are not built yet, is [the Plan 07 design](../plans/2026-10-05-nous-mcp-alphaxiv-parity-design.md), a dated record and not a contract.

- **Binding.** A consent request, the grant exchanged from it and each renewal bind exactly one of a project (Collection) or a workspace. The request and context schemas enforce it, and so do CHECK constraints added by migration `hb03_workspace_grants`; an action row must name a target project, its grant's workspace, or both. The workspace must be one the signed-in user owns or is a live member of, and a public workspace alone is not access. `authorized_scope` (`backend/src/services/integrations/context.py`) resolves what a grant may touch on every call: a project grant gets its one live Collection, and a workspace grant gets every live Collection of its workspace. A deleted workspace, a lapsed membership, or an inactive user or organization is refused with 403, and a deleted Collection drops out of a workspace grant's scope.
- **MCP-only.** A workspace grant can never hold `harness:execute`, `artifacts:publish`, `handoff:read` or `handoff:write`: `check_scopes` refuses them when consent is requested and on every use, and the harness socket and the artifact routes refuse a workspace grant as well, because a harness run, an output folder and a chat handoff each belong to one project. `connect --workspace` therefore needs `--tools`, refuses `--publish`, `--chat` and `--handoff`, and does not request `harness:execute`. `nous-harness run` and `workspace add` refuse a workspace connection and point to `--project`; `mcp install` still prints the standalone Codex command. Reconnecting with `--workspace` replaces the previous connection and does not carry registered local folders over, and the CLI says so. `request_action` refuses a workspace grant too (422, `workspace connections cannot request this action`), because `create_project_note` cannot choose a project; the bridge still offers `request_action` when `tools:write` is held, and the call fails with that 422 until Plan 07 Slice 3.
- **Project selector.** On a workspace grant every tool that works on one project (the project-scoped tools under **Read tools**, and `list_project_artifacts`) advertises an optional `project_id`. The arXiv and connector tools, `get_arxiv_paper_content` and `list_library` act on no single project and advertise none; a caller that sends one gets 422 (unknown argument). It selects one project and is not identity. It must be a UUID and never a name (422 otherwise), and it must be one of the workspace's live Collections as `authorized_scope` computes them on that call (403 otherwise). Leaving it out returns the tool error `project_id_required`. A project grant still rejects `project_id` as an unknown argument (422), and every grant rejects `user_id`, `organization_id`, `thread_id`, `run_id` and `grant_id`.
- **`library:read`.** Adds `list_library`: one page of the folders (Collections) the grant may use, ordered by name, each with `id`, `name`, a description cut to 500 characters and its live `document_count`. `limit` is 1-50 (default 50) and `offset` starts at 0; `next_offset` is `null` on the last page. A page ends early when its names and descriptions would pass the 64 KiB result cap (it is measured in UTF-8 bytes, and 50 long CJK or emoji descriptions do), so it can hold fewer than `limit` folders: continue from `next_offset`, never from `offset + limit`. A project grant sees its one project. `GET /api/v1/integrations/tools` lists only the tools a grant's scopes may call, and calling a tool outside them is refused with 403 even when the grant holds `tools:read`.
- **`library:write`.** Consent only for now. The scope is accepted, stored on the grant and shown on the approval page, but no library action exists and nothing checks it; `request_action` still supports only `create_project_note`, which always needs the browser approval described above. `library:write` needs `library:read` and `tools:write`, and `library:read` needs `tools:read`; a consent request or grant missing one of them is refused with 403. `connect --library` asks for both library scopes. A connection that holds `library:write` also launches the MCP child with `--library`, which only marks the session for Plan 07 Slice 3.
- **Auto-run rule (Plan 07 Slice 3, not built).** The approved design lets the reversible library actions (`save_papers_to_folder`, `remove_papers_from_folder`, `move_papers_between_folders`, `create_folder`, `rename_folder`, `update_document_metadata`) run inside the request and return a completed receipt when the grant holds `library:write`. A grant with `tools:write` alone keeps the approval page for every action, and `delete_folder` and `ingest_arxiv_papers` always keep it, whatever the grant holds. Until Plan 07 Slice 3 ships, `library:write` is a consent the backend does not yet act on, so do not describe any library change as running without approval.
- **Approval page.** `/integrations/approve` shows a **Workspace** row instead of **Project** for a workspace consent, and each scope as a plain-language label beside its raw name (`frontend/src/lib/integrations/scopeLabels.ts`). A scope without a label falls back to its raw name, so a label cannot hide a scope. The `library:write` label says it adds, removes, moves and renames items in the workspace without asking each time and that deleting folders and ingesting papers still need approval; it describes the behavior Plan 07 Slice 3 adds. The action review page names the workspace for an action that has no project.
- **Rollback.** The migration's downgrade deletes every workspace-bound request and grant and every action without a project before it restores `project_id NOT NULL`, so rolling it back ends all workspace connections.

## Consent, disclosure, and isolation limits

Consent is separate from CLI login: the browser authorizes the CLI user, then an authenticated browser approves the device grant for one project or, for a workspace connection, one workspace. `nous-harness disconnect` revokes this device's access. It renews its stored grant if needed and calls `DELETE /api/v1/integrations/grants/{grant_id}` with the CLI token and that grant. That call revokes the grant and the consent it was exchanged from, so the grant cannot be renewed and approved note requests under that consent no longer execute. After the revocation commits it also moves the owner's CLI revoked-before cutoff, described below. The command then removes the local credentials. If NOUS cannot be reached or returns a server error while the stored grant is less than 15 minutes old, nothing is removed and the command can be retried.

The route sets `end_cli_sessions` on `revoke_integration_grant` only for a CLI-token caller, so revoking a grant from a browser session leaves CLI logins alone. CLI tokens carry no device ID, so the cutoff is per user: **every CLI login of that user ends, not only this computer's, and the other computers must run `nous-harness connect` again.** A computer whose login ended this way is refused (401) when it tries to revoke, so its own `disconnect` only removes its local credentials and its consent stays valid. The cutoff is a best-effort Redis write. If Redis is unreachable the write is skipped without a retry, the server only logs a warning, the DELETE still returns 204, the command still reports success, and the CLI login stays valid until it expires (30 days by default). `CLI_TOKEN_REVOCATION_FAIL_CLOSED` only governs how reads treat an unreachable store.

`disconnect` cannot revoke anything once the stored grant has expired, because an expired grant can be neither renewed nor used to authorize the revoke call. The grant ages from `connect` or its last renewal, so a bridge that has been stopped for more than 15 minutes lands here. If renewal is refused, or NOUS is unreachable or returns a server error for a grant that old, `GrantKeeper` raises `GrantExpired` and `disconnect` removes the local credentials. It does the same when NOUS refuses the revoke call itself (401, 403 or 404) and for a connection made before grant renewal shipped, which has no stored grant ID. In each case the command prints a pointer to `/integrations/devices` and **neither revokes the consent nor ends the CLI login.** The grant itself lapses within 15 minutes of its last renewal, but the consent stays valid until it is revoked another way, and approved note requests under it still execute, because the executor re-checks the consent and not the grant token. To be sure the consent is revoked, run `disconnect` while `nous-harness run` is still running or within 15 minutes of the last renewal.

The only shipped revoke route is `DELETE /api/v1/integrations/grants/{grant_id}`. With a CLI token it needs that grant to be live. A signed-in browser session may also call it for a grant it owns, but no shipped route or screen lists grant IDs and `disconnect` discards the stored one. The browser page for listing and revoking connected devices, `/integrations/devices` (which the CLI messages point to), is in open PR #1788 and is **not shipped**. There is no user-facing device or grant revocation screen yet, so a consent that `disconnect` could not revoke has no shipped way to be revoked. Deleting local state without `disconnect` stops this bridge instance but does not revoke the server grant. Revocation prevents further grant-authorized work, but does not itself terminate a native process already accepted by Codex. The local CLI state uses owner-only permissions and stores access/grant credentials behind an opaque handle.

NOUS persists the accepted user message, assistant text deltas, tool lifecycle summaries, usage, native approval targets, and terminal events in its chat/run records. Codex receives the prompt and executes local work. Keep secrets out of prompts and workspace output unless they are intended to be processed by both systems. The browser receives IDs and labels, not local absolute workspace paths or CLI grant tokens.

The app-server start/resume policy is checked against the configured workspace-write sandbox, writable roots, approval policy, reviewer, and network setting. This does **not** provide a folder-only read guarantee: registering a root identifies the requested write scope; it is not proof that Codex cannot read files outside that root. The feature treats the local computer and data available to the Codex process as trusted execution context. Optional MCP configuration is locally composed and session-scoped, never supplied by the browser.

Command requests support one-time allow/deny. File-change requests stay deny-only until the persisted backend request schema carries a disclosed path or concrete change summary. An item ID or generic reason is insufficient review context. Unknown request shapes, persistent grants, changed approval targets, expired/revoked grants, and stale decisions fail closed.

## Recovery and operational controls

The local journal records native command intent before sending it. If acceptance or an interrupt is ambiguous, the bridge does not replay that action and retains the workspace lock while it reconciles exact Codex history. An unmatched or unverifiable native action remains quarantined; restarting the bridge with the same state allows reconciliation to continue. Do not remove the journal, clear the lock manually, or treat a WebSocket close/interrupt receipt as proof that Codex stopped.

For an uncertain interrupt that still cannot reconcile, stop the bridge and run:

```sh
pnpm --filter @nous/harness-bridge start recover-interrupt
```

The command lists exact interrupt command IDs. Recovery is permitted only with verified boot identity on the same macOS/Linux computer. If a legacy record has no baseline, the first invocation records one; wait at least ten seconds, reboot that same computer, then run:

```sh
pnpm --filter @nous/harness-bridge start recover-interrupt --command COMMAND_UUID
```

Recovery removes only that interrupt's uncertain-delivery blocker. It preserves run outcome and workspace ownership; restart the bridge so normal reconciliation can supply terminal evidence. Same-boot, different-machine, or unavailable OS evidence is rejected. Do not edit the SQLite journal by hand.

`HARNESS_BRIDGE_ENABLED` is the backend kill switch and defaults to `false`. Setting it to `false` rejects newly accepted Codex chat work and prevents pending start commands from dispatching. Reads, cancellation, and reconciliation of already accepted runs remain available to bring work to a known state. After disabling the feature, monitor outstanding runs until they have terminal outcomes before retiring their paired device.

## Conformance and live acceptance

The package conformance test verifies that every capability an adapter advertises has a corresponding callable operation. The pinned Codex fixture tests exercise the app-server protocol and policy checks; the conformance helper alone does not prove a Codex binary or remote service is available. Additional adapters remain gated until conformance and their operation-specific fixture contract tests pass.

The Playwright live acceptance is opt-in and uses a dedicated, project-bound test thread and workspace on a real paired device running the bridge. It asks Codex to execute a harmless, unique marker-file command; it expects an exact command-approval request, reloads the chat while the request is pending, approves once, and verifies the persisted user/assistant marker appears only once after completion and another reload. It annotates the NOUS thread and accepted run IDs. It intentionally does not expose or log local credential material. The native Codex session ID is not exposed to the browser and is not claimed by this test.

Configure `NOUS_HARNESS_E2E=1`, `NOUS_HARNESS_E2E_DEVICE_ID`, `NOUS_HARNESS_E2E_WORKSPACE_ID`, `NOUS_HARNESS_E2E_THREAD_ID`, `NOUS_HARNESS_E2E_EMAIL`, and `NOUS_HARNESS_E2E_PASSWORD` to enable the live scenario. The named workspace must point to a disposable local test fixture, the thread must be bound to the same NOUS project, the device bridge must be running, and the backend kill switch must be enabled. Without opt-in/device/credentials the test reports **skipped / NOT RUN** with the missing prerequisite in its reason. Skipped is never counted as live acceptance. Report local fixture tests, hosted CI job/SHA, and live-device outcome separately; for live runs include the NOUS thread and run IDs recorded in Playwright annotations. CI without those dedicated secrets and a connected device has no live result.

From the repository root, run the focused conformance suite with:

```sh
pnpm --filter @nous/harness-bridge test -- test/conformance.test.ts
```

Run the separately configured browser acceptance with:

```sh
pnpm --dir tests/e2e exec playwright test harness-bridge.spec.ts --project=chromium
```
