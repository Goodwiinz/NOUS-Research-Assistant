# Local Codex harness bridge

**Status:** Implemented as a local Codex bridge feature; live acceptance requires a deliberately configured NOUS test project, paired device, and workspace, and has **NOT RUN** against a deployment. This document describes the current bridge contract. It does not cover cross-chat context synchronization or tracing. Through the opt-in local stdio MCP facade described in [NOUS read tools over MCP](#nous-read-tools-over-mcp), Codex can call NOUS read tools, publish one file from a registered workspace root as a NOUS artifact, and request a project note that the user must approve in the browser, each only under a scope the user approved. Selecting project memories to share (`context:read`), artifact editing and artifact sharing are not exposed.

## User workflow

1. An owner runs `nous-harness connect` on the computer that will execute Codex. The CLI completes NOUS browser authorization, registers the device, and waits for browser consent to a project-scoped `harness:execute` grant.
2. The owner registers a local workspace root, starts `nous-harness run`, and selects **Local Codex**, the paired computer, and its workspace in the NOUS chat composer.
3. NOUS durably accepts the chat message and run before dispatch. The local bridge receives a fenced command over authenticated WSS and starts the pinned Codex app-server with the verified local policy. Persisted events flow back to the existing chat transcript.
4. Exact, one-time Codex command approvals and required input are shown in NOUS. The browser re-reads the saved request before a decision and sends only the decision plus the displayed target hash. The local CLI grant token never enters the browser.
5. If the browser disconnects, execution continues and NOUS can replay persisted events when the chat reconnects. Browser presence is not run ownership or terminal evidence.

NOUS-native chat remains the default provider. Provider/device/workspace selection is scoped to the signed-in user and chat thread. The bridge does not search or continue other NOUS conversations or synchronize a context file. Codex reaches NOUS only through the opt-in MCP facade below, and only with the scopes approved for this device.

## NOUS read tools over MCP

`nous-harness mcp` is a local stdio MCP server (`packages/harness-bridge/src/mcp/`) that forwards `tools/list` and `tools/call` to the backend read gateway (`GET/POST /api/v1/integrations/tools[/read]`, gated by `NOUS_MCP_ENABLED`, default `false`). The backend owns the tool allowlist, JSON Schema catalog, argument validation, project scoping, and result bounds; the facade adds nothing a caller could use to widen them.

- **Read tools.** The catalog carries two kinds of tool. Project-scoped tools resolve the Collection from the grant, never from arguments, and return `requested_documents_unavailable` for any document outside it (a foreign id and an unknown id are indistinguishable): `search_documents`, `list_project_documents`, `do_kb_retrieve`, `get_current_draft`, `get_document_content` (summary or full text, paginated by characters with `offset`/`limit` ≤ 48,000 and a `next_offset` to follow until it is `null`) and `retrieve_passages` (PostgreSQL full-text ranking over the project's documents, `document_ids` optional, `top_k` ≤ 20; the `answer_pdf_queries` analog that works with `DO_KB_ENABLED=false`), `find_researchers` and `get_researcher` (see **Researcher tools** below). Args-only tools take no identity and are dispatched before the project check: `search_arxiv` (120 s budget shared with the agent's slow tier, at most 20 results advertised, arXiv itself returns up to 5), `search_external_database` and `list_external_databases` (connector registry, at most 20 results), and `get_arxiv_paper_content` (full text of one arXiv id, paginated like `get_document_content`, cached in Redis: 24 h fresh, up to 7 d stale fallback when a refetch fails). `get_arxiv_paper_content` persists nothing; use `ingest_arxiv_papers` to add a paper to NOUS. Every result is capped at 64 KiB; upstream failures come back as stable tool errors (`upstream_timeout`, `upstream_unavailable`, `arxiv_unavailable`, `retrieval_unavailable`, `researcher_not_found`) and never carry exception text. `source_refs` list only observed identities: `document_id`, `draft_id`, `arxiv_id`, or `external_id` with its `connector`.
- **Researcher tools.** `find_researchers` (`query` 1-200 characters, `limit` ≤ 25, default 10) returns `{researchers: [{researcher_id, name, paper_count}]}` and `get_researcher` (`researcher_id`) returns `{researcher: {researcher_id, name}, papers: [{document_id, title, arxiv_id?, published?}], coauthors: [{researcher_id, name, paper_count}]}`, with `source_refs` of one `document_id` per listed paper (`find_researchers` returns none). Both read one source: `Document.document_metadata["authors"]`, the author list that arXiv ingest persists, of the grant's live project documents (the same project-and-ancestors join as every other project-scoped tool). **Coverage is the author lists of papers ingested into the bound project.** Documents without an author list are invisible. NOUS stores no affiliations, institutions or career history for them, and the tools do not claim any. Because the index is the project's own documents, another project's papers and authors in the same organization can never appear, and an author who only wrote for another project answers `researcher_not_found`, the same as an unknown id. (The knowledge graph's `PERSON` entities are not used: the graph is scoped by organization only and carries no document ids, so it cannot be restricted to a project.) A `researcher_id` is the author's name casefolded with whitespace collapsed (at most 200 characters), so spelling variants merge and `name` is the newest document's spelling; two different people with the same name are one researcher. `find_researchers` matches the query as a case-insensitive substring and orders by paper count, then name. `get_researcher` lists at most 100 papers (newest `publication_date`/`published` first, then newest ingest) and at most 100 co-authors, counted over every paper of the researcher, not only the listed ones. The tools scan the 2,000 newest documents of the project in Python (O(documents × authors)); when a list is cut, by that scan window, the 100-item caps or the 64 KiB result cap, the payload carries `truncated: true`. Live proof (ingest an arXiv paper into a dev project, then call both tools) has **NOT RUN**; the tests use SQLite project and document fixtures only.
- **Consent.** `nous-harness connect --tools` requests `harness:execute` plus `tools:read`; adding `--publish` also requests `artifacts:publish`, and adding `--write` also requests `tools:write`. `--publish` and `--write` are refused without `--tools`. Every scope appears on the browser approval page. `tools:read` covers the whole read catalog above, including the arXiv and external-connector searches, which leave NOUS to query third-party services with the model-supplied query. A connection made without `--tools` has no MCP access and `mcp install` refuses with a reconnect hint. The stored scopes only decide whether the local process offers a tool; the backend re-checks the grant on every request.
- **Managed sessions.** When the local connection carries `tools:read`, `nous-harness run` adds a session-scoped `mcpConfig` entry that launches `nous-harness mcp --api ORIGIN --store DIR --session HANDLE` for that Codex thread. Argv contains only the API origin, the state directory, and the opaque credential handle; the CLI JWT and grant token are read from the owner-only store inside the child.
- **Standalone Codex.** `nous-harness mcp install` prints the `codex mcp add nous -- …` command for the user to run. The package never edits `~/.codex/config.toml` or any other global Codex configuration.
- **Transport hygiene.** Stdout is the JSON-RPC channel; diagnostics go to stderr. The API origin must be HTTPS, except the explicit loopback development hosts. Model-supplied arguments are sent only inside the invocation body; they cannot set headers, URLs, identity, or credentials. Gateway rejections are stable tool errors with no retry: 401 → reconnect with `--tools`; 403 → grant lacks `tools:read` or the resource is outside the granted project; 422 → the gateway's own argument reason; 503 → NOUS's own reason (tools disabled, artifact publication disabled, or artifact storage unavailable). Network failures name the URL and the underlying cause on stderr. `run` logs a stderr notice when the connection has no `tools:read`, so a missing `nous` server is never silent.
- **Publication.** When the connection carries `artifacts:publish` (`connect --tools --publish`), managed sessions launch the MCP child with `--root <registered workspace root>` and the server offers `artifacts_publish` (`packages/harness-bridge/src/artifacts/`). Each call validates the relative path lexically, refuses symlinked or hard-linked files, then opens the file with containment enforced on the descriptor rather than the path string: macOS uses `O_NOFOLLOW_ANY` so the kernel refuses a symlink in any component (a directory swapped for a symlink after the path checks fails with `ELOOP`), Linux checks the opened descriptor's real path under `/proc/self/fd` against the root, and other platforms are refused. Size is compared before and after the open and the read is bounded to the validated size. The bytes are then reserved, uploaded and finalized through `/api/v1/artifacts` with the grant headers; the backend re-verifies size, digest and scope, and serves downloads as attachments with `nosniff`. Publication is gated by `ARTIFACTS_ENABLED` (default `false`), not by `NOUS_MCP_ENABLED`: with it off, reserve, upload and finalize answer 503 "Artifact publication is disabled". `mcp install` binds the single registered root, or the one named with `--root`; several registered roots require an explicit choice. A root that no longer exists at launch is logged to stderr and publication is simply not offered; read tools keep working. **The root is a publish scope, not a read boundary:** under Codex `workspace-write` the model can copy any file it can read into the root and publish it, exactly as it could write it to disk. That matches Plan 01's stated limit that folder registration is not read isolation.
- **Note requests.** When the connection carries `tools:write` (`connect --tools --write`), managed sessions launch the MCP child with `--actions` and the server also offers `request_action` and `get_action_status` (`packages/harness-bridge/src/actions/`). `request_action` supports only `action=create_project_note` with a client-generated UUID `invocation_id`, a title (at most 255 characters), Markdown content (at most 200,000 characters) and up to 20 tags; identity and project come from the grant, never from arguments. It calls `POST /api/v1/integrations/actions`, which records the request idempotently by invocation ID and payload and returns `awaiting_approval` with an `approval_url` for the browser page `/integrations/actions/{invocation_id}`. Nothing is created until the signed-in requester opens that page, reviews the stored title, content and project, and approves. The decision route (`POST /api/v1/integrations/actions/{invocation_id}/decision`) refuses every CLI token, so a harness cannot approve its own request. The `drain_integration_actions` beat task (every 2 s) claims each approved row with a conditional update, re-checks authority against the consent the grant was exchanged from rather than the short-lived grant token, and then creates the note and its receipt in one transaction. A commit with an ambiguous outcome leaves the row `executing`. When `SWEEPERS_ENABLED` is on, `sweep_stale_actions` moves such rows to `outcome_unknown`, and they are never re-run. `get_action_status` reports `awaiting_approval`, `approved`, `executing`, `succeeded`, `failed` (including a denial) or `outcome_unknown`. `NOUS_MCP_ENABLED=false` rejects new requests and holds approved rows unexecuted, while status reads of existing requests keep working. The backend guard lives in `backend/src/services/agent/tool_actions.py`.
- **Grant renewal.** Integration grants live 15 minutes. The bridge and each MCP child share one credential handle and keep it fresh with `GrantKeeper` (`packages/harness-bridge/src/grants.ts`). Once the stored grant is 10 minutes old, it renews through `POST /api/v1/integrations/grants/{grant_id}/renew`. Long-running processes check every 2 minutes, and the replacement is written back to the owner-only store so other processes pick it up. Renewal revokes the old grant token and issues a new one with the same consent, project and scopes. It cannot widen scopes or revive an expired, revoked or consent-revoked grant. A publish sequence (reserve, upload, finalize) is pinned to one grant and starts only on a grant at most 5 minutes old. Connections made before renewal shipped have no stored grant ID, so they stop after 15 minutes and must reconnect.
- **Tests.** `packages/harness-bridge/test/mcp.test.ts` spawns both the managed configuration and the standalone command against a recording HTTP server and asserts identical `source_refs`, correct grant headers, JSON-RPC-only stdout, no secrets in the config or install command, and no writes under `CODEX_HOME`. `test/actions.test.ts`, `test/grants.test.ts` and `test/disconnect.test.ts` cover note requests, renewal and disconnect against stubbed HTTP responses. The backend action tests run on SQLite, so the conditional row claim under concurrent PostgreSQL workers is **NOT RUN**. Live acceptance against a real Codex and NOUS deployment is **NOT RUN** by these suites.

## Consent, disclosure, and isolation limits

Consent is separate from CLI login: the browser authorizes the CLI user, then an authenticated browser approves the device/project grant. `nous-harness disconnect` revokes this device's access. It renews its stored grant if needed and calls `DELETE /api/v1/integrations/grants/{grant_id}` with the CLI token and that grant. That call revokes the grant and the consent it was exchanged from, so the grant cannot be renewed and approved note requests under that consent no longer execute. After the revocation commits it also moves the owner's CLI revoked-before cutoff, described below. The command then removes the local credentials. If NOUS cannot be reached or returns a server error while the stored grant is less than 15 minutes old, nothing is removed and the command can be retried.

The route sets `end_cli_sessions` on `revoke_integration_grant` only for a CLI-token caller, so revoking a grant from a browser session leaves CLI logins alone. CLI tokens carry no device ID, so the cutoff is per user: **every CLI login of that user ends, not only this computer's, and the other computers must run `nous-harness connect` again.** A computer whose login ended this way is refused (401) when it tries to revoke, so its own `disconnect` only removes its local credentials and its consent stays valid. The cutoff is a best-effort Redis write. If Redis is unreachable the write is skipped without a retry, the server only logs a warning, the DELETE still returns 204, the command still reports success, and the CLI login stays valid until it expires (30 days by default). `CLI_TOKEN_REVOCATION_FAIL_CLOSED` only governs how reads treat an unreachable store.

`disconnect` cannot revoke anything once the stored grant has expired, because an expired grant can be neither renewed nor used to authorize the revoke call. The grant ages from `connect` or its last renewal, so a bridge that has been stopped for more than 15 minutes lands here. If renewal is refused, or NOUS is unreachable or returns a server error for a grant that old, `GrantKeeper` raises `GrantExpired` and `disconnect` removes the local credentials. It does the same when NOUS refuses the revoke call itself (401, 403 or 404) and for a connection made before grant renewal shipped, which has no stored grant ID. In each case the command prints a pointer to `/integrations/devices` and **neither revokes the consent nor ends the CLI login.** The grant itself lapses within 15 minutes of its last renewal, but the consent stays valid until it is revoked another way, and approved note requests under it still execute, because the executor re-checks the consent and not the grant token. To be sure the consent is revoked, run `disconnect` while `nous-harness run` is still running or within 15 minutes of the last renewal.

The only shipped revoke route is `DELETE /api/v1/integrations/grants/{grant_id}`. With a CLI token it needs that grant to be live. A signed-in browser session may also call it for a grant it owns, but no shipped route or screen lists grant IDs and `disconnect` discards the stored one. The browser page for listing and revoking connected devices, `/integrations/devices` (which the CLI messages point to), is in open PR #1788 and is **not shipped**. There is no user-facing device or grant revocation screen yet, so a consent that `disconnect` could not revoke has no shipped way to be revoked. Deleting local state without `disconnect` stops this bridge instance but does not revoke the server grant. Revocation prevents further grant-authorized work, but does not itself terminate a native process already accepted by Codex. The local CLI state uses owner-only permissions and stores access/grant credentials behind an opaque handle.

NOUS persists the accepted user message, assistant text deltas, tool lifecycle summaries, usage, native approval targets, and terminal events in its chat/run records. Codex receives the prompt and executes local work. Keep secrets out of prompts and workspace output unless they are intended to be processed by both systems. The browser receives IDs and labels, not local absolute workspace paths or CLI grant tokens.

The app-server start/resume policy is checked against the configured workspace-write sandbox, writable roots, approval policy, reviewer, and network setting. This does **not** provide a folder-only read guarantee: registering a root identifies the requested write scope; it is not proof that Codex cannot read files outside that root. The feature treats the local computer and data available to the Codex process as trusted execution context. Optional MCP configuration is locally composed and session-scoped, never supplied by the browser.

Command requests support one-time allow/deny. File-change requests stay deny-only until the persisted backend request schema carries a disclosed path or concrete change summary. An item ID or generic reason is insufficient review context. Unknown request shapes, persistent grants, changed approval targets, expired/revoked grants, and stale decisions fail closed.

## Recovery and operational controls

The local journal records native command intent before sending it. If acceptance or an interrupt is ambiguous, the bridge does not replay that action and retains the workspace lock while it reconciles exact Codex history. An unmatched or unverifiable native action remains quarantined; restarting the bridge with the same state allows reconciliation to continue. Do not remove the journal, clear the lock manually, or treat a WebSocket close/interrupt receipt as proof that Codex stopped.

For an uncertain interrupt that still cannot reconcile, stop the bridge and run:

```sh
pnpm --filter @nous/harness-bridge start recover-interrupt
```

The command lists exact interrupt command IDs. Recovery is permitted only with verified boot identity on the same macOS/Linux computer. If a legacy record has no baseline, the first invocation records one; wait at least ten seconds, reboot that same computer, then run:

```sh
pnpm --filter @nous/harness-bridge start recover-interrupt --command COMMAND_UUID
```

Recovery removes only that interrupt's uncertain-delivery blocker. It preserves run outcome and workspace ownership; restart the bridge so normal reconciliation can supply terminal evidence. Same-boot, different-machine, or unavailable OS evidence is rejected. Do not edit the SQLite journal by hand.

`HARNESS_BRIDGE_ENABLED` is the backend kill switch and defaults to `false`. Setting it to `false` rejects newly accepted Codex chat work and prevents pending start commands from dispatching. Reads, cancellation, and reconciliation of already accepted runs remain available to bring work to a known state. After disabling the feature, monitor outstanding runs until they have terminal outcomes before retiring their paired device.

## Conformance and live acceptance

The package conformance test verifies that every capability an adapter advertises has a corresponding callable operation. The pinned Codex fixture tests exercise the app-server protocol and policy checks; the conformance helper alone does not prove a Codex binary or remote service is available. Additional adapters remain gated until conformance and their operation-specific fixture contract tests pass.

The Playwright live acceptance is opt-in and uses a dedicated, project-bound test thread and workspace on a real paired device running the bridge. It asks Codex to execute a harmless, unique marker-file command; it expects an exact command-approval request, reloads the chat while the request is pending, approves once, and verifies the persisted user/assistant marker appears only once after completion and another reload. It annotates the NOUS thread and accepted run IDs. It intentionally does not expose or log local credential material. The native Codex session ID is not exposed to the browser and is not claimed by this test.

Configure `NOUS_HARNESS_E2E=1`, `NOUS_HARNESS_E2E_DEVICE_ID`, `NOUS_HARNESS_E2E_WORKSPACE_ID`, `NOUS_HARNESS_E2E_THREAD_ID`, `NOUS_HARNESS_E2E_EMAIL`, and `NOUS_HARNESS_E2E_PASSWORD` to enable the live scenario. The named workspace must point to a disposable local test fixture, the thread must be bound to the same NOUS project, the device bridge must be running, and the backend kill switch must be enabled. Without opt-in/device/credentials the test reports **skipped / NOT RUN** with the missing prerequisite in its reason. Skipped is never counted as live acceptance. Report local fixture tests, hosted CI job/SHA, and live-device outcome separately; for live runs include the NOUS thread and run IDs recorded in Playwright annotations. CI without those dedicated secrets and a connected device has no live result.

From the repository root, run the focused conformance suite with:

```sh
pnpm --filter @nous/harness-bridge test -- test/conformance.test.ts
```

Run the separately configured browser acceptance with:

```sh
pnpm --dir tests/e2e exec playwright test harness-bridge.spec.ts --project=chromium
```
